---
title: Cron jobs
description: Schedule commands from the desired document or with crontab.
---

Declare an instance's jobs in `desired.json`, or install them with `crontab` inside the app. A
deployment whose document declares jobs runs those alone.

## Configure the host

Add `[cron]` to `config.toml`:

```toml
[cron]
max_jobs_per_app = 10
time_zone = "Europe/Zurich"
```

Both settings are required and have no defaults.

- `max_jobs_per_app` limits the jobs an app can install or declare.
- `time_zone` sets the IANA time zone for all apps.

## Declare jobs in the document

Give the instance a [`cron`](/docs/reference/desired) list:

```json
"cron": [
  {
    "name": "retry",
    "schedule": "*/5 * * * *",
    "command": "./server cron retry",
    "timeoutS": 300,
    "backoffMs": [10000, 60000]
  }
]
```

| Field | Meaning |
| --- | --- |
| `name` | The job's ID in logs and in `reported.json`. Unique in the instance. |
| `schedule` | When it runs, in the [schedule syntax](#schedule-syntax). |
| `at` | Instead of `schedule`: one run, due as soon as the host sees it at or after this instant. |
| `command` | One line for the shell. |
| `timeoutS` | Seconds an attempt may last. |
| `backoffMs` | Delays before each [retry](#runs) of a failed attempt: at most 5, each at most an hour. |

- The list is the deployment's whole table. Changing it under the same `deploymentId` restarts
  nothing.
- A job is its name and its schedule. A job that keeps both keeps its next run when the rest of
  the list changes, or when the list is emptied and declared again.
- An `at` entry runs once. A host that restarts sees it again as new.
- `crontab FILE`, `crontab -` and `crontab -r` fail with
  `crontab: this deployment's jobs are declared by its document`. `crontab -l` prints the
  scheduled jobs, each under a `# name` line.
- An instance without `cron` keeps its guest's crontab.

## Install a crontab

Run these commands inside the app:

| Command | Action |
| --- | --- |
| `crontab /app/crontab` | Install a file. |
| `crontab -l` | Print the installed crontab. |
| `crontab -r` | Remove the crontab. |

To install from standard input:

```sh
printf '0 * * * * /app/bin/cleanup\n' | crontab -
```

Installing a crontab replaces all jobs. Invalid crontabs leave the previous jobs unchanged.

## Schedule syntax

Schedules have five fields followed by a command:

```text
minute hour day-of-month month day-of-week command
```

Fields accept lists, ranges, steps, and month or weekday names. Supported aliases are `@hourly`,
`@daily`, `@midnight`, `@weekly`, `@monthly`, `@yearly`, and `@annually`. `@reboot` is rejected.

Environment assignments apply to the jobs below them:

```text
MODE=maintenance
30 2 * * * /app/bin/cleanup
```

Jobs use the host's time zone. A different `CRON_TZ` is rejected. During daylight saving changes,
skipped times shift forward by the clock change. Repeated times run once.

## Execution

The host wakes sleeping apps to run due jobs. Commands run with the app's user, working
directory, and environment, using `/bin/sh` or `SHELL` if set. Crontab assignments override the
app's environment.

- Running commands keep the guest awake.
- A job runs once at a time. A job due while it still runs is skipped; other jobs run beside it.
- The host does not replay jobs missed while the daemon was stopped.
- Editing or removing a crontab changes future runs. Running commands continue.

Standard output and standard error go to the app's [logs](/docs/guides/logs-and-metrics),
between two lines the host writes:

```text
cron retry started (scheduled 2026-10-24T16:15:00Z, attempt 1)
cron retry completed exit 0 after 344 ms
```

Each line carries the job ID, the run ID (`<instant>/<attempt>`), and the attempt's trace and
span. Each attempt is a trace: the command gets `TRACEPARENT`, so the spans and records the app
exports join it.

## Runs

A run of a declared job is one or more attempts.

| Outcome | Exit | Reason | Retried |
| --- | --- | --- | --- |
| The command exited 0 | `0` | | No |
| It exited with another code, or was killed by a signal (128 plus the signal) | the code | | Yes |
| It outlasted `timeoutS`: its process group is killed | `124` | `timeout` | Yes |
| Its deployment was stopped or replaced | | `cancelled: deployment replaced` | No |
| The guest refused to start it | | `rejected: busy`, `rejected: spawn` or `rejected: malformed` | No |
| The job was still running when this run was due | | `skipped: previous run still running` | No |

A retry waits for the next delay of `backoffMs`, under a new attempt number and a new trace. It
is dropped when the job is due again first or is running.

When the [telemetry sink](/docs/guides/logs-and-metrics#ship-logs-and-metrics-to-a-bucket) is
configured and the instance carries `labels.app` and `labels.timeline`, each attempt has a record
at `cron/<app>/<timeline>/<job>/<instant>/<attempt>`, with `/` and `%` in the timeline escaped as
`%2F` and `%25`. `<instant>` is the scheduled minute, or a declared run's `at`, as
`2026-10-24T16:15:00Z`.

1. The host creates the record before the attempt starts, and only if it is not there yet:
   `host`, `rev`, `deployment`, `trace`, `started`, and `manual` for an `at` run.
2. It overwrites it once when the attempt ends, adding `ended`, `exit`, `duration_ms`, `status`
   (`completed` or `failed`) and `reason`.

<Callout title="One attempt across hosts">
  A host that finds the record already there does not run the attempt and writes no line:
  another host, or this one before a restart, took it. `nibrunner_cron_attempts_taken_total`
  counts these. Two hosts given the same table run each attempt once.
</Callout>

Without the sink, declared jobs run without records.

`reported.json` lists each instance's scheduled jobs as `instances[].cron`, in table order:
`jobId` (the job ID its log lines carry: a declared job's `name`), `schedule`, `commandDigest`
(the SHA-256 of the command in hex, never the command itself) and `nextRun`. `at` entries are not
listed. Only the deployment that declared or installed the jobs lists them.

Stopping an app cancels running commands and pauses scheduling. Replacing or removing a
deployment also removes its crontab. The host waits for cancelled runs before stopping the guest.
New deployments must declare or install their own jobs.

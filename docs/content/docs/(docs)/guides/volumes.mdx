---
title: Volumes
description: What a volume starts with, where volumes are stored, and how to back one up.
---

An app has one volume or one scratch. Either is the writable top of the app's root filesystem: all
writes go there. A volume is declared in `volumes`, pointed at with `volumeId`, and is the only
thing that gets backed up. A scratch is named on the instance and is gone with its microVM.

```json
"volumes": [
  { "volumeId": "vol-1", "appId": "app-1", "sizeBytes": 8589934592, "desiredState": "present" }
]
```

## Scratch instead of a volume

An instance that keeps nothing names `scratch` in place of `volumeId`, and the document lists no
volume for it:

```json
"instances": [
  { "appId": "app-1", "scratch": { "kind": "memory", "mib": 512 }, "...": "..." }
]
```

| `kind` | Where the writes go | What it costs |
| --- | --- | --- |
| `memory` | A tmpfs of `mib` in the guest | The guest's memory: `mib` may not exceed `config.resources.memoryMib`, and what is written counts against the tenant's ceiling |
| `disk` | A sparse ext4 file of `mib`, made under `paths.state_dir` | The host's disk, as it is written |

- A scratch starts empty at every cold boot, so a restart, a replacement, a new `deploymentId` or
  a stop and start all start from nothing.
- It is kept through sleep and wake: a memory scratch is in the snapshot, and a disk scratch
  stays on the host until the microVM is stopped.
- It is never reported in `volumes`, never checkpointed and never exported.

<Callout title="Sizing a memory scratch">
  A memory scratch is part of the guest's RAM, so size `config.resources.memoryMib` — and
  `limits.memoryMib`, if you set it — to hold the program and the scratch together. The host adds
  nothing for it on its own.
</Callout>

## Seeding a volume from an archive

A volume is formatted empty the first time it appears in `desired.json`. To start it with
content, name an archive in the artifact store and where to unpack it:

```json
"volumes": [
  {
    "volumeId": "vol-1", "appId": "app-1", "sizeBytes": 8589934592, "desiredState": "present",
    "initialContents": {
      "digest": "<sha256 of the archive, lowercase hex>",
      "objectKey": "seeds/app-1",
      "destinationPath": "/app/data"
    }
  }
]
```

- The archive is a tar, gzipped or not, or a zip.
- Entries are unpacked under `destinationPath`: `nested/hello.txt` becomes
  `/app/data/nested/hello.txt`. The directory and everything in it are owned by uid 65534.
- Files the archiver added on its own are skipped: `.DS_Store`, `__MACOSX`, `Thumbs.db`, editor
  swap files.
- The volume fails, with the reason in `reported.json`, if an entry escapes `destinationPath`, a
  zip contains a symlink, or the archive does not fit.

<Callout title="Note">
  The archive is unpacked once, when the volume is formatted. Changing or removing
  `initialContents` on an existing volume has no effect.
</Callout>

## Storage backends

`volumes.backend` in `config.toml` selects one of two backends. The
[reference](/docs/reference/config) lists every key of both.

### `local-file`

```toml
[volumes]
backend = "local-file"
storage_prefix = "host-1"
```

Volumes are sparse files under `paths.state_dir`. There is nothing else to configure. A
`[volumes.zerofs]` section on this backend is an error, not ignored. This is the installer's
default.

The limitation: volumes do not survive the machine. Checkpoints and exports are not supported on
this backend, because they are taken in the object store.

### `zerofs`

```toml
[volumes]
backend = "zerofs"
storage_prefix = "host-1"

[volumes.zerofs]
binary = "/opt/nibrunner/bin/zerofs"
config_file = "/etc/zerofs/config.toml"
mount_path = "/mnt/zerofs"
nbd_socket_path = "/run/zerofs/nbd.sock"
ninep_socket_path = "/run/zerofs/9p.sock"
rpc_socket_path = "/run/zerofs/rpc.sock"
storage_url = "s3://my-bucket/host-1"
cache_dir = "/data/zerofs"
cache_disk_gib = 200
cache_memory_gib = 2
checkpoint_runtime_dir = "/run/zerofs-checkpoint"
checkpoint_config_file = "/etc/zerofs/checkpoint.toml"
checkpoint_cache_dir = "/data/zerofs-checkpoint"
```

Volume blocks live in an object store and reach the guest over NBD, through
[ZeroFS](https://github.com/Barre/ZeroFS). `install` generates ZeroFS's configuration files and
systemd units from these keys, so this section is the only place to configure it. The
object-store credentials and the encryption password go in `host.env`.

- **Size `cache_disk_gib` for the disk it is on.** It shares that disk with the snapshots in
  `paths.snapshot_dir`. Losing a snapshot costs one cold boot. Filling the disk breaks the
  filesystem every app on the host runs from.
- **Use whole gibibytes.** The daemon subtracts `cache_memory_gib` from the memory it can promise
  to guests, and reads the value back from the file it generated, which truncates fractions.
- **Slot _N_ uses `/dev/nbdN`.** `install` loads the nbd module with `max_apps + 1` minors. If
  the module is already loaded with fewer, it is not reloaded, because that would detach every
  device under every guest. Raising `max_apps` on this backend therefore needs a reboot.

<Callout type="warn" title="Warning">
  `volumes.storage_prefix` is per host, not per app. Every volume on the host shares it. Deleting
  the prefix destroys all of them.
</Callout>

## Checkpoints and exports

On the `zerofs` backend, `desired.json` can take a point-in-time copy of a volume and bundle it
as an archive:

```json
"checkpoints": [
  { "checkpointId": "ckpt-1", "volumeId": "vol-1", "desiredState": "present" }
],
"exports": [
  {
    "exportId": "exp-1", "appId": "app-1", "volumeId": "vol-1",
    "objectKey": "exports/app-1/bundle.tar.gz", "desiredState": "present",
    "environment": { "DATABASE_URL": "sqlite:///app/data.db" }
  }
]
```

- A **checkpoint** is a copy of the volume at the moment it was taken. It stays in the object
  store until `desiredState` is `absent`.
- An **export** freezes the guest's filesystem, takes its own checkpoint, and writes a gzipped
  tar to `objectKey` in `exports.store_url`. The tar holds the volume's contents under `data/`
  and `environment` as `.env`. To start a new volume from it, point `initialContents` at an
  archive of the `data/` contents, with `destinationPath` `/`.

`reported.json` reports the state of each checkpoint and export, with the reason on failure.

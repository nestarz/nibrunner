---
title: Host capacity
description: How many apps a host is sized for, what the machine can hold, and how to change it.
---

`max_apps` is a top-level key in [`config.toml`](/docs/reference/config), above every section:

```toml
max_apps = 300
```

Everything sized by slot count follows from it: the slot ring, the eight loopback ports each slot
reserves from 21000, the nbd minors on a `zerofs` host, the 1024 conntrack entries per app, and
`nibrunner_slots{of="total"}` on the metrics page. A full host reports it by naming this key.

## What the machine can hold

`install` measures three limits, assuming each app uses 1 vCPU, 256 MiB of memory and an 8 GiB
volume:

| Limit | How it is computed |
| --- | --- |
| Runs at once | Guest memory (total, minus the host and the storage cache) divided by 256 MiB. |
| Holds on disk | The disk under `paths.snapshot_dir`, minus the storage cache and an 8 GiB reserve, divided by the size of one snapshot. On a `local-file` host, one volume per app is added to that size. |
| Fits on ports | 5567. Each slot reserves eight ports from 21000, and the last one must be at most 65535. |

The installer sets `max_apps` to the lowest of the three, with a comment above the key listing
all three. Every `nibrunnerd start` prints the three limits against the configured value:

```
max_apps = 300: assuming an app is 1 vCPU, 256 MiB and 8 GiB to start, this host runs 29 at once, holds 320 on disk, and fits 5567 on its ports; above 29 counts on apps sleeping
```

Exceeding the memory limit is only reported. That is what [sleeping](/docs/guides/sleep-and-wake)
is for. Exceeding the disk or port limit makes `start` print the value to set instead. Both are
advice, not errors: an app with more resources counts for more, and the value is yours to set.

### Unused guest pages

The bundled guest reports unused pages through Firecracker's virtio balloon device. The host can
reclaim their physical memory without reducing the guest's configured memory limit. The balloon
target remains zero; no polling controller or forced inflation is used. The bundled kernel must
enable `CONFIG_MEMORY_BALLOON`, `CONFIG_VIRTIO_BALLOON` and `CONFIG_PAGE_REPORTING`.

This can reduce resident memory and improve snapshot compressibility. Full snapshots still read
all guest memory, and guests may allocate their full limit again. Admission therefore continues
to reserve the configured limit. Reporting is not a promise that more guests fit concurrently.

### The memory limit is enforced

Each reported instance can include a `memory` reading from its host cgroup: current and peak
bytes, swap bytes, memory pressure totals, high-limit events and OOM kills, the cgroup's own
`limits`, and the VMM's proportional and anonymous resident sets. An absent reading
means that the cgroup could not be measured, not that the VM uses no memory. The peak is optional
on kernels that do not expose it. Regular readings travel with the report heartbeat; a new OOM
is reported immediately. These observations do not change admission or increase a VM's limit.

A reconcile pass boots an app only if its memory fits alongside every app that is up or starting,
including the ones started earlier in the same pass. An app that does not fit stays `pending`,
with the shortfall on its record
(`waiting to be started: its host is 256 MiB short of the memory it needs`). No start attempt is
consumed, and it is retried every pass. So if `desired.json` names a thousand on-request apps on
a host that runs 240 at once, 240 boot and the rest follow as the first ones sleep. A wake that
does not fit is refused the same way, and its request gets a 503. The number of waiting starts
is logged once per pass and counted in
`nibrunner_start_refusals_total{reason="no_room"}`.

### Measured admission

By default a start or a wake must fit beside the ceiling of every VM that is up. To admit against
what VMs actually use, start by observing:

```toml
[memory_admission]
mode = "observe"
headroom_mib = 1024
```

Every start, wake and snapshot then logs `memory admission evaluated` with the strict shortfall
it was decided on and the measured one beside it, and nothing it decides changes. Set
`mode = "adaptive"` to decide by the measurement once it agrees with what you expect. Restart the
daemon after changing the section.

A running VM is counted at its observed peak, swapped pages and proportional set included, plus
the greater of 25 percent or 64 MiB, up to its cgroup ceiling. A VM that is starting, or whose
sample is missing, old or from an earlier process, counts at its full ceiling, unless its
deployment was measured before: each deployment's peak is kept for 30 days, across restarts and
after it is gone, so a cold start or a wake of a known revision is admitted at what it ran at.
Targets must fit the guest-memory budget, and expected growth must fit `MemAvailable` less
`headroom_mib`. Every start and wake holds what it was admitted at until its VM is measured
running, so two of them never fit into the same room, and a snapshot holds its VM's whole
ceiling until it is written.

### A bounded workload pool

```toml
[memory_admission.pool]
slice = "workloads.slice"
memory_mib = 4096
```

The operator creates the root-level slice and bounds it; its `memory.max` must be positive and
no larger than `memory_mib`, or the daemon does not start. Every VMM's cgroup is then placed under
`<slice>/nibrunner-jailer`, and admission also respects what is left of the slice below its
`memory.high` (clean inactive file cache counted as free). Until every VM that holds memory has
been restarted inside the pool, adaptive admission falls back to ceilings. Set `memory.high` below
`memory.max` to start reclaim before the hard limit.

### Reclaiming quiet apps

```toml
[memory_admission]
reclaim = true
```

Before a start or a wake is refused for memory, and whenever `MemAvailable` drops under
`headroom_mib`, the pool nears its `memory.high`, or the kernel reports memory stalls, quiet
`on-request` apps with a `traffic-idle` policy are put to sleep one at a time: `build` first,
then `preview`, `standard` and `production` (the `limits.memory.priority` of each), the longest
quiet first within each. An app with a request open, a raw port, activity in the last 30 seconds
or a start in the last minute is left up, and a deployment never puts a `production` app to sleep
to make room. Reclaim stops once the host is back above `headroom_mib` plus a quarter.

### External memory reservations

`memory.sock` in the host runtime directory accepts root-local requests from a process in a
service or scope cgroup. Each JSON frame has a four-byte, big-endian length prefix and is limited
to 16 KiB. The request and reply types are in `protocol::memory`.

Before starting an external service, send:

```json
{
  "operation": "acquire",
  "id": "03ae9139-c7fc-4ad4-a94b-6e3c81d3b406",
  "unit": "example-build.service",
  "memory_mib": 1024
}
```

Use a new UUID for each operation. Start work only after `status: granted`, with its cgroup
`MemoryMax` set to the granted budget. A `waiting` reply names the capacity or service condition
to retry. Repeating the same request from the same process returns the same grant.
Changing its owner, unit or budget is rejected.
Set optional `minimum_mib` to accept a smaller grant when the preferred `memory_mib` does not fit.
The reply gives the actual budget to enforce. Grants never fall below the minimum; fixed requests
continue to require the full requested budget. Retrying a flexible request returns its original grant.

After the service exits, send `{"operation":"release","id":"03ae9139-c7fc-4ad4-a94b-6e3c81d3b406"}`.
Release waits for an inactive or failed service with no queued job and no live processes.
A build with several services can name their shared `.slice` instead. Apply the granted limit
to that slice, including the build parent. An active slice keeps its reservation until its
whole cgroup is empty and it has no queued job.
Disconnecting does not release capacity. Reservations are written before the grant and restored
before app admission after a daemon restart. Automatic cleanup also waits for the owner process
and its cgroup to exit, so an orphaned launcher cannot start work after its budget was released.
An invalid ledger row prevents startup instead of discarding reservations. Leases are kept in the `memory_leases` table and are only good for the boot they were granted in.

External grants share the app reservation lock. They always require fresh physical headroom;
strict and observation modes also enforce the configured host budget. They hold their full
grant until release. Existing build tools must connect to this API before adaptive admission
can account for them.

When the owner already runs inside the granted service or slice, admission tracks that cgroup's
identity. Its resident anonymous memory is already absent from host available RAM, so only the
remaining grant counts as future growth. The full grant still counts against the host budget.
File cache and swap receive no discount. Missing, replaced, overlapping, or unbounded groups keep
their full reservation. A service created after its grant also keeps the full reservation.
With a workload pool, a lease is granted only to work already running inside it. A lease also
leaves room for the largest `production` app asleep or frozen to wake.


## Changing it

1. Edit `max_apps`.
2. Run `nibrunnerd start`.

Raising only `max_apps` on a `local-file` host grows its capacity in place. Existing slots and
open proxy connections stay where they are. `start` reports `reloaded`; repeating it with the
same configuration reports `running`. A changed executable, startup file, or other setting
still takes the restart path.

<Callout title="Note">
  - **Raising it on a `zerofs` host needs a reboot.** The nbd module is loaded with
    `max_apps + 1` minors, which cannot be changed in place. `start` says so rather than
    reloading a module with volumes attached.
  - **Lowering it below a slot an app occupies moves that app** to a new slot on the next start,
    with a new loopback port and a new guest address.
</Callout>

### From the desired state

A control plane that places apps can raise the count without touching `config.toml`: it sets
`maxApps` in the [desired state](/docs/reference/desired).

```json
{
  "hostId": "host-1",
  "revision": "deploy-42",
  "maxApps": 128,
  "volumes": [],
  "instances": [],
  "checkpoints": [],
  "exports": []
}
```

The running daemon widens its slots to `maxApps` when it reads the document, and again when it
restarts on it. No `nibrunnerd start` is needed, and `nibrunner_slots{of="total"}` shows
the new count.

| `maxApps` | What the host holds |
| --- | --- |
| absent, or at most `max_apps` | `max_apps` |
| above `max_apps` | `maxApps` |
| refused | `max_apps`, with a warning in the daemon's log naming why |

<Callout title="Note">
  - **It only raises.** A document never takes a host below `max_apps`, and a running daemon
    never narrows: a lower `maxApps` takes effect on the next restart, with the same move for an
    app past it as lowering `max_apps`.
  - **It is held to the rules `max_apps` is held to:** at most 5567, and no listener of yours in
    the wider range of loopback ports. A `zerofs` host refuses it, for the reason above.
  - **The conntrack table stays sized for `max_apps`**, never below 262144 entries. Past 256 apps,
    raise `max_apps` itself and run `nibrunnerd start` to resize it.
  - **Each slot runs its VMM as its own jailer identity**, taken from the range `nibrunnerd
    install` reserves in `/etc/subuid` and `/etc/subgid` (65536 of each). A slot past that range
    is refused at boot instead of borrowing someone else's identity.
</Callout>

## HTTP concurrency

By default the HTTP router imposes no concurrency limit. To bound requests across
apps and per app, add an optional section under your HTTP listener in `config.toml`:

```toml
[proxy.http.concurrency]
host_concurrent = 128
app_concurrent = 16
```

These are example capacities, not measured application throughput. Values must be
between 1 and 65535. The per-app ceiling applies automatically to every app,
including newly added apps. All hostnames of an app share its limit. Run
`nibrunnerd start` after changing host configuration. This restarts the daemon when
needed, interrupting proxy connections, without redeploying guests.

A full app or host returns HTTP 503 with `Retry-After: 1` immediately. Requests
waiting for a cold start, uploads, streaming response bodies and upgraded connections keep
their permits until they finish or disconnect. An ordinary request releases its permit only
after both its upload and response finish or are dropped. No waiting queue is created. Unknown
hostnames do not allocate concurrency state. This covers the hostname router, not raw
ports, guest-to-guest connections or the private activator listeners. Limits bound
proxy work; they do not cancel work a tenant continues after a client disconnects.

## Concurrent VM starts

The required top-level [`max_concurrent_vm_starts`](/docs/reference/config#hostconfig-max_concurrent_vm_starts)
in `config.toml` bounds simultaneous Firecracker boots and snapshot restores.
The installer writes `2`; values must be between 1 and 65535. Existing configs
must add this key before starting the updated daemon. Run `nibrunnerd start`
after changing it.

```toml
max_concurrent_vm_starts = 2
```

A full budget refuses a start immediately rather than queuing it. Reconciliation
uses its existing retry path; callers waking an app receive the existing start
failure. Requests for an app already being woken still share its single wake.
A cold boot holds its permit until the guest's control port accepts a connection,
confirming PID 1 initialized. A restore holds it through the guest clock-sync and
release handshake. A guest that does not initialize within 60 seconds is stopped
and releases its permit. Deferred boots remain pending without spending the app's
restart budget. Application health checks, artifact preparation and volume
attachment are outside this limit. HTTP request concurrency is separate.


## VM CPU and memory limits

Every new VM boot and snapshot restore applies cgroup v2 limits through the
Firecracker jailer. The app's [`resources`](/docs/reference/desired#instanceresources)
in desired state supplies both values; no additional host configuration is needed.

| Resource | Host limit |
| --- | --- |
| CPU | `vcpuCount` host CPUs in aggregate, over each 100 ms period. |
| Memory | `memoryMib` plus 64 MiB and 12.5% of guest RAM for Firecracker and kernel overhead. |
| Swap | Disabled for the VM process. |

For example, a VM with 1 vCPU and 256 MiB of guest RAM has a 100% CPU ceiling and
a 352 MiB host memory ceiling. CPU limits throttle the whole VMM, including its
I/O threads. Exceeding the memory ceiling can kill the VM; its existing restart
policy handles that exit. The allowance is covered by guest boot, memory pressure,
sleep and restore tests; it does not reserve physical memory or change admission.

While Firecracker is paused for a snapshot, its memory ceiling temporarily adds
one guest RAM to cover the snapshot's filesystem cache. A failed sleep removes
the allowance before resuming the guest. A completed sleep releases the stopped
VMM's cgroup; retained snapshot pages remain host storage charges rather than
consuming the restored VM's running limit. This also applies to snapshots on tmpfs.

The host must provide the cgroup v2 CPU and memory controllers. If limits cannot
be applied, the VM fails to start. Existing VMs keep their current limits until
their next boot or restore; restarting the daemon readopts them.

### Per-instance limits

An instance's optional `limits` tighten what its `resources` give it, and are applied without a
new deployment: a running VM's cgroup is rewritten when the document changes, and a sleeping one
takes them as it wakes.

```json
"limits": {
  "concurrent": 8,
  "cpuPercent": 25,
  "memory": { "targetMib": 384, "swapMib": 512, "priority": "preview" }
}
```

| Field | Effect |
| --- | --- |
| `concurrent` | Requests the proxy carries to this instance at once, in place of `app_concurrent`. The host-wide limit still applies. |
| `cpuPercent` | `cpu.max` quota in percent of one core, never above `vcpuCount` cores: `25` is a quarter of a core. |
| `memory.targetMib` | The working-set target, capped at the guest's memory. It never changes the hard ceiling. |
| `memory.swapMib` | `memory.swap.max`. `0` keeps the VM out of swap, as without `limits`. |
| `memory.priority` | `production` holds its target with `memory.low` and an OOM score of −500; `standard` changes nothing; `preview` and `build` are throttled at their target with `memory.high` and score 500 and 1000. |

While a snapshot is written, `memory.high` is lifted so that a throttled VM does not take longer
to sleep, and restored if the sleep fails.

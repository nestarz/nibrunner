title: Host capacity
description: How many apps a host is sized for, what the machine can hold, and how to change it.
---

`max_apps` is the first key in [`config.toml`](/docs/reference/config), above every section:

```toml
max_apps = 300
```

Everything sized by slot count follows from it: the slot ring, the eight loopback ports each slot
reserves from 21000, the nbd minors on a `zerofs` host, the 1024 conntrack entries per app, and
`nibrunner_slots{of="total"}` on the metrics page. A full host reports it by naming this key.

## What the machine can hold

`install` measures three limits, assuming each app uses 1 vCPU, 256 MiB of memory and an 8 GiB
volume:

| Limit | How it is computed |
| --- | --- |
| Runs at once | Guest memory (total, minus the host and the storage cache) divided by 256 MiB. |
| Holds on disk | The disk under `paths.snapshot_dir`, minus the storage cache and an 8 GiB reserve, divided by the size of one snapshot. On a `local-file` host, one volume per app is added to that size. |
| Fits on ports | 5567. Each slot reserves eight ports from 21000, and the last one must be at most 65535. |

The installer sets `max_apps` to the lowest of the three, with a comment above the key listing
all three. Every `nibrunnerd start` prints the three limits against the configured value:

```
max_apps = 300: assuming an app is 1 vCPU, 256 MiB and 8 GiB to start, this host runs 29 at once, holds 320 on disk, and fits 5567 on its ports; above 29 counts on apps sleeping
```

Exceeding the memory limit is only reported. That is what [sleeping](/docs/guides/sleep-and-wake)
is for. Exceeding the disk or port limit makes `start` print the value to set instead. Both are
advice, not errors: an app with more resources counts for more, and the value is yours to set.

### Unused guest pages

The bundled guest reports unused pages through Firecracker's virtio balloon device. The host can
reclaim their physical memory without reducing the guest's configured memory limit. The balloon
target remains zero; no polling controller or forced inflation is used. The bundled kernel must
enable `CONFIG_MEMORY_BALLOON`, `CONFIG_VIRTIO_BALLOON` and `CONFIG_PAGE_REPORTING`.

For traffic-idle apps, the host requests one guest reclaim after half the idle timeout, with a
minimum quiet period of 30 seconds. Open requests, stale activity readings and always-running
apps prevent this request. The guest requests up to 64 MiB of file-backed cache reclaim per quiet
period, with a 500 ms execution budget. The kernel can reclaim more or less than requested.
A failed or partial reclaim does not stop the app.
The kernel reports free blocks from 64 KiB, so smaller free regions can return to the host.
Reclaim runs before the sleep deadline to give page reporting time to complete.

This can reduce resident memory and improve snapshot compressibility. Full snapshots still read
all guest memory, and guests may allocate their full limit again. Admission therefore continues
to reserve the configured limit by default. Reporting is not a promise that more guests fit concurrently.

### The memory limit is enforced

Each reported instance can include a `memory` reading from its host cgroup: current and peak
bytes, proportional resident bytes (PSS), swap bytes, memory pressure totals, high-limit events
and OOM kills. The cgroup path is included when available. An absent reading
means that the cgroup could not be measured, not that the VM uses no memory. The peak is optional
on kernels that do not expose it. Regular readings travel with the report heartbeat; a new OOM
is reported immediately. These observations do not increase a VM's limit.

A reconcile pass boots an app only if its memory fits alongside every app that is up or starting,
including the ones started earlier in the same pass. An app that does not fit stays `pending`,
with the shortfall on its record
(`waiting to be started: its host is 256 MiB short of the memory it needs`). No start attempt is
consumed, and it is retried every pass. So if `desired.json` names a thousand on-request apps on
a host that runs 240 at once, 240 boot and the rest follow as the first ones sleep. A wake that
does not fit is refused the same way, and its request gets a 503. The number of waiting starts
is logged once per pass and counted in
`nibrunner_start_refusals_total{reason="no_room"}`.

### Measured admission

Start with observation mode. It logs the strict and measured shortfalls for each start or wake,
while enforcing the existing strict decision:

```toml
[memory_admission]
mode = "observe"
headroom_mib = 1024
reclaim = true
```

Restart the daemon after changing this section. Omit it to retain strict admission without
additional sampling. Set `mode = "adaptive"` to enforce the measured decision after validation.

A running VM reserves the largest of its cgroup peak, current usage and PSS, including swapped
pages, plus the greater of 25 percent or 64 MiB, up to its enforced ceiling. PSS includes resident
snapshot mappings that can be charged to another cgroup. Without a kernel peak, current usage is used.
New and starting VMs reserve their full host memory budget. Missing, old, unbounded or
previous-process samples also reserve the full budget, as do readings without PSS.
Samples must be at most five seconds old.
If another reservation starts or ends while samples are collected, the decision discards working-set
discounts and counts full ceilings. Adaptive admission waits when host readings are missing or stale.
Targets must fit the host's guest-memory budget; expected growth and concurrent startup
reservations must also fit `MemAvailable` after the configured headroom. Swap capacity is not
added to this budget.

A measured frozen VM reserves its resident footprint. Its swapped pages do not count as expected
growth while it remains paused. A wake or snapshot must reserve its full budget before resuming it.
Full snapshots fault in guest memory even when the paused footprint is small. Their reservations
share the start/wake pool and remain held until the operation finishes. Under strict admission,
snapshotting reuses the VM's existing full budget so an overcommitted host can still drain.
Cancelling the caller leaves the snapshot task running with its reservation and per-app transition
lock until it completes. Memory samples also verify the VM's process start time before and after
reading the cgroup and PSS, so a reused PID cannot supply another process's working set.

Adaptive admission can admit guests whose combined ceilings exceed physical RAM. External work
must use the reservation API below; unregistered builds are not coordinated. Admission does not
guarantee capacity for simultaneous growth. Keep observation mode until the workload and pressure
handling are validated.

### External memory reservations

`memory.sock` in the host runtime directory accepts root-local requests from a process in a
service or scope cgroup. Each JSON frame has a four-byte, big-endian length prefix and is limited
to 16 KiB. The request and reply types are in `protocol::memory`.

Before starting an external service, send:

```json
{
  "operation": "acquire",
  "id": "03ae9139-c7fc-4ad4-a94b-6e3c81d3b406",
  "unit": "example-build.service",
  "memory_mib": 1024
}
```

Use a new UUID for each operation. Start work only after `status: granted`, with its cgroup
`MemoryMax` set to the granted budget. A `waiting` reply names the capacity or service condition
to retry. Repeating the same request from the same process returns the same grant.
Changing its owner, unit or budget is rejected.
Set optional `minimum_mib` to accept a smaller grant when the preferred `memory_mib` does not fit.
The reply gives the actual budget to enforce. Grants never fall below the minimum; fixed requests
continue to require the full requested budget. Retrying a flexible request returns its original grant.

After the service exits, send `{"operation":"release","id":"03ae9139-c7fc-4ad4-a94b-6e3c81d3b406"}`.
Release waits for an inactive or failed service with no queued job and no live processes.
A build with several services can name their shared `.slice` instead. Apply the granted limit
to that slice, including the build parent. An active slice keeps its reservation until its
whole cgroup is empty and it has no queued job.
Disconnecting does not release capacity. Reservations are written before the grant and restored
before app admission after a daemon restart. Automatic cleanup also waits for the owner process
and its cgroup to exit, so an orphaned launcher cannot start work after its budget was released.
A corrupt ledger prevents startup instead of discarding reservations.

External grants share the app reservation lock. They always require fresh physical headroom;
strict and observation modes also enforce the configured host budget. They hold their full
grant until release. Existing build tools must connect to this API before adaptive admission
can account for them.

When the owner already runs inside the granted service or slice, admission tracks that cgroup's
identity. Its resident anonymous memory is already absent from host available RAM, so only the
remaining grant counts as future growth. The full grant still counts against the host budget.
File cache and swap receive no discount. Missing, replaced, overlapping, or unbounded groups keep
their full reservation. A service created after its grant also keeps the full reservation.

### Reclaim before refusing capacity

`reclaim = true` enables reclaim independently of admission mode. Omit it or set it to `false`
to disable automatic reclaim. A refused start first tries to snapshot quiet on-request apps,
then retries admission after each successful sleep, up to four apps. Deployment admission
protects production apps; request-triggered wakes can reclaim idle production as a last resort.
The reclaim lock waits at most 30 seconds. Snapshot time is additional.

The activity pass also reclaims one app when `MemAvailable` falls below headroom, or memory PSI
over ten seconds reaches 10 percent `some` or 1 percent `full`. Recovery requires headroom plus
the larger of 25 percent or 256 MiB, with PSI below 2 percent `some` and 0.2 percent `full`.
If PSI is unavailable, only available memory is used.

Quiet builds and previews sleep first, followed by standard and production apps. Reclaim requires
fresh activity readings, no open requests, at least 30 seconds without traffic and 60 seconds
since start or restore. Only traffic-idle policies qualify. Apps with a transition in progress
are skipped, and each attempt has a 60-second cooldown. Active streams and always-running work
are protected. Apps with raw ports are excluded: established connections can bypass proxy
accounting, so a quiet packet counter does not prove that they have no active connections.
Snapshots preserve rollback state, but disk latency still affects sleep and wake.

The optional [frozen tier](/docs/guides/sleep-and-wake#frozen-tier) keeps recently quiet VMs
paused in memory before their snapshot deadline. It can reclaim pages into configured host
swap without first writing a full snapshot. Frozen VMs remain accounted for in admission;
compressed swap is not additional guaranteed capacity.

## Changing it

1. Edit `max_apps`.
2. Run `nibrunnerd start`.

Raising only `max_apps` on a `local-file` host grows its capacity in place. Existing slots and
open proxy connections stay where they are. `start` reports `reloaded`; repeating it with the
same configuration reports `running`. A changed executable, startup file, or other setting
still takes the restart path.

<Callout title="Note">
  - **Raising it on a `zerofs` host needs a reboot.** The nbd module is loaded with
    `max_apps + 1` minors, which cannot be changed in place. `start` says so rather than
    reloading a module with volumes attached.
  - **Lowering it below a slot an app occupies moves that app** to a new slot on the next start,
    with a new loopback port and a new guest address.
</Callout>

## HTTP concurrency

By default the HTTP router imposes no concurrency limit. To bound requests across
apps and per app, add an optional section to `config.toml`:

```toml
[http_admission]
host_concurrent = 128
app_concurrent = 16

[http_admission.apps]
app-one = 8
```

These are example capacities, not measured application throughput. Values must be
between 1 and 65535. App overrides use app IDs; all hostnames of an app share its
limit. Run `nibrunnerd start` after changing the limits. They apply in place and
existing requests stay counted until they finish. Lowering a limit below the
number already active refuses new requests until enough have finished.

A full app or host returns HTTP 503 with `Retry-After: 1` immediately. Requests
waiting for a cold start, streaming response bodies and upgraded connections keep
their permits until they finish or disconnect. No waiting queue is created. Unknown
hostnames do not allocate admission state. This covers the hostname router, not raw
ports, guest-to-guest connections or the private activator listeners. Limits bound
proxy work; they do not cancel work a tenant continues after a client disconnects.
## Concurrent VM starts

The optional top-level `max_concurrent_vm_starts = 2` in `config.toml` bounds
simultaneous Firecracker boots and snapshot restores. Omit it to preserve the
existing behavior. Values must be between 1 and 65535. Run `nibrunnerd start`
after changing configuration.

A full budget queues a start for up to 30 seconds. A slot released during that
window lets the waiting start proceed. After the timeout, reconciliation uses its
existing retry path; callers waking an app receive the existing start failure.
Cancelling a waiter releases its place in the queue. Requests for an app already
being woken still share its single wake.
The permit covers VM boot/restore work, not the app's entire health grace period,
artifact preparation or volume attachment. HTTP request admission is separate.

## VM process budgets

Each desired instance runs in its own systemd scope directly under the root slice. This lets
`memory.low` protect production without being capped by an unprotected parent slice.
Without an explicit budget,
the hard limit is its declared guest RAM plus 64 MiB of VMM overhead, and its CPU
quota is 100 percent per guest vCPU. Use `vm_budgets` to override these defaults.

```toml
[vm_budgets.default]
cpu_percent = 100
memory_mib = 2304

[vm_budgets.apps.app-one]
cpu_percent = 50
memory_mib = 1280
```

100 percent means one host CPU, independently of guest vCPU count. The memory
budget includes guest RAM **and Firecracker overhead**; choose it above the guest's
configured RAM. The kernel can kill a VM exceeding its limit. Scope swap is disabled by default.
These limits do not reserve capacity for the host or replace guest RAM admission.

An optional `memory` policy in an instance's `limits` sets its working-set target,
host swap allowance, and priority:

```json
{
  "concurrent": 256,
  "cpuPercent": 100,
  "memoryMib": 1280,
  "memory": { "targetMib": 384, "swapMib": 512, "priority": "production" }
}
```

Production protects the target with `memory.low`. Preview and build priorities
use the target as `memory.high`, which throttles allocation and triggers reclaim.
The target is capped at the hard limit; it does not resize guest RAM. OOM scores
are -500 for production, 0 for standard, 500 for previews, and 1000 for builds.
These priorities influence reclaim and OOM selection; they cannot guarantee survival.
Set the target from measured usage plus a margin. Host swap must be configured
separately, and its physical compression ratio is not a capacity guarantee.

Run `nibrunnerd start` to load the budgets without restarting the proxy. Budgets apply on subsequent VM
boots and snapshot restores; existing VM processes retain their scopes and limits.
Removing overrides restores the default budget on subsequent starts. The daemon can restart and
re-adopt scoped VMs normally. Linux and systemd with CPU and memory accounting are
required. Each VM receives its configured OOM priority instead of inheriting the daemon's protection.

Starts and request-triggered wakes reserve capacity through the same controller.
Reservations end after the instance record accounts for the process, or when the
attempt is cancelled. This prevents simultaneous starts from claiming the same RAM.

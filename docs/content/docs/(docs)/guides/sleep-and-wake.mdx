---
title: Sleep and wake
description: When an app sleeps, and what wakes it.
---

An app with no traffic is snapshotted and suspended. The next request wakes it. This is how a
host [holds more apps than it can run at once](/docs/guides/host-capacity). Which apps sleep, and
after how long, is set per instance in `desired.json`.

## Desired state

`desiredState` says whether an instance should be up:

| `desiredState` | Behaviour |
| --- | --- |
| `running` | Keep the microVM up. |
| `on-request` | Start it on first deploy and on every request that arrives while it sleeps. Let it sleep in between. |
| `stopped` | Stop the microVM. Requests to its hostnames get a 503. |

## When it sleeps

`activation.sleepWhen` says what puts an `on-request` instance to sleep:

```json
{
  "desiredState": "on-request",
  "activation": {
    "sleepWhen": { "kind": "traffic-idle", "timeoutMs": 900000 }
  }
}
```

| `sleepWhen` | The microVM is suspended when |
| --- | --- |
| `{ "kind": "traffic-idle", "timeoutMs": N }` | No client-initiated traffic for `N` ms. A request or stream the proxy is still carrying counts as activity, however quiet it is. Replies to the guest's own outbound connections do not renew activity. |
| `{ "kind": "max-lifetime", "ttlMs": N }` | It has been up for `N` ms, busy or not. A request still open at that point is given up to 30 s more to finish. |
| `{ "kind": "never" }` | Never. Only `desired.json` takes it down. |

Without `sleepWhen`, an `on-request` instance sleeps after five minutes idle. Any other
`desiredState` never sleeps.

<Callout title="Note">
  - Only an `on-request` instance may set a `sleepWhen` other than `never`. Nothing would wake
    any other kind, and the next reconcile pass would start it again. A file that does this is
    rejected as a whole.
  - `idleTimeoutMs` is the old spelling of `sleepWhen: traffic-idle`. A file that sets both is
    rejected.
  - A host that has not managed to read an app's traffic lately leaves it up rather than taking
    the silence for quiet, and says so in its log. `max-lifetime` runs on the clock either way.
</Callout>

## Frozen tier

To pause quiet apps before writing a snapshot, set an optional threshold in host configuration:

```toml
[memory_admission]
mode = "observe"
headroom_mib = 1024
reclaim = true
freeze_after_ms = 60000
```

Only `on-request` apps with a `traffic-idle` policy qualify. The threshold must precede the
snapshot deadline; values below 30 seconds use 30 seconds. Open requests, recent wakes,
missing activity readings and declared background work prevent freezing.
Apps with raw ports also remain running until their normal sleep deadline: established raw
connections can bypass the proxy's open-request accounting, so they cannot yet enter this tier.

| Reported state | Memory and wake behavior |
| --- | --- |
| `running` | The app executes normally. |
| `frozen` | The tenant is frozen and the VM is paused. A request resumes the existing VM, synchronizes its clock and waits for readiness. |
| `idle` | The VM has been snapshotted and stopped. A request restores its snapshot. |

The host requests guest cache reclaim before freezing, then up to 64 MiB of host cgroup reclaim.
Firecracker's native pause API stops the vCPUs; its API thread remains available. The host cgroup
continues to enforce memory limits and supports reclaim without entering the host freezer.
Thaw resumes the VM before synchronizing the guest clock. This requires the pause/resume vsock fix in Firecracker
1.16.2. VMs retained from an older daemon wait for their next start before entering this tier.
With host swap and a per-VM swap allowance, reclaim can move pages into zram. Compression,
retained memory and wake latency depend on the workload; freezing does not imply zero RAM.
Frozen apps retain their admission budget. Their original idle deadline still applies, and
memory pressure can select them for earlier snapshots. Within each priority, frozen apps are
selected before running apps.

The daemon records freeze intent before pausing and recovers it after a restart. Health and
guest usage probes skip frozen apps. Changing the policy to require continued execution thaws
them. Omit `freeze_after_ms` to disable new automatic freezes; requests still wake existing ones.

Snapshots record their Firecracker version. An older or unknown snapshot format falls back to
a cold start with the existing volume; upgrades do not attempt to load an incompatible snapshot.

## What wakes it

Any inbound traffic: an HTTP request on one of its hostnames, or anything on a
[raw port](/docs/guides/raw-ports). The connection is accepted and held, then forwarded once the
app's [health check](/docs/guides/health-checks) passes. The client sees a slow first response,
not a refused connection.

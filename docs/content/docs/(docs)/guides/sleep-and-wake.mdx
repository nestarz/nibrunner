---
title: Sleep and wake
description: When an app sleeps, and what wakes it.
---

An app with no traffic is snapshotted and suspended. The next request wakes it. This is how a
host [holds more apps than it can run at once](/docs/guides/host-capacity). Which apps sleep, and
after how long, is set per instance in `desired.json`.

## Desired state

`desiredState` says whether an instance should be up:

| `desiredState` | Behaviour |
| --- | --- |
| `running` | Keep the microVM up. |
| `on-request` | Start it on first deploy (or on its first request, with a [lazy first boot](#first-boot)) and on every request that arrives while it sleeps. Let it sleep in between. |
| `stopped` | Stop the microVM. Requests to its hostnames get a 503. |

## When it sleeps

`activation.sleepWhen` says what puts an `on-request` instance to sleep:

```json
{
  "desiredState": "on-request",
  "activation": {
    "sleepWhen": { "kind": "traffic-idle", "timeoutMs": 900000 }
  }
}
```

| `sleepWhen` | The microVM is suspended when |
| --- | --- |
| `{ "kind": "traffic-idle", "timeoutMs": N }` | No client-initiated traffic for `N` ms. A request or stream the proxy is still carrying counts as activity, however quiet it is. Replies to the guest's own outbound connections do not renew activity. |
| `{ "kind": "max-lifetime", "ttlMs": N }` | It has been up for `N` ms, busy or not. A request still open at that point is given up to 30 s more to finish. |
| `{ "kind": "never" }` | Never. Only `desired.json` takes it down. |

Without `sleepWhen`, an `on-request` instance sleeps after five minutes idle. Any other
`desiredState` never sleeps.

<Callout title="Note">
  - Only an `on-request` instance may set a `sleepWhen` other than `never`. Nothing would wake
    any other kind, and the next reconcile pass would start it again. A file that does this is
    rejected as a whole.
  - `idleTimeoutMs` is the old spelling of `sleepWhen: traffic-idle`. A file that sets both is
    rejected.
  - A host that has not managed to read an app's traffic lately leaves it up rather than taking
    the silence for quiet, and says so in its log. `max-lifetime` runs on the clock either way.
  - A sleep that does not happen leaves the app up. The host tries again after 30 s, then waits
    twice as long after each further failure, up to 10 minutes. Traffic in between resets the
    wait.
</Callout>

## Frozen tier

A host can pause quiet apps in place before their snapshot deadline:

```toml
[memory_admission]
mode = "observe"
headroom_mib = 1024
freeze_after_ms = 60000
```

Only `on-request` apps with a `traffic-idle` policy qualify, and only once they have been quiet for
`freeze_after_ms` (at least 30 seconds) and up for a minute, with no request open, no raw port and
a fresh traffic reading. The tenant is held through the guest's own freeze, Firecracker's vCPUs
are paused, and the kernel is asked to reclaim up to 64 MiB of the VMM's cgroup.

| Reported state | What it costs, and what a request does |
| --- | --- |
| `running` | The app runs. |
| `frozen` | Its memory stays resident (less what the kernel reclaimed); nothing is scheduled. A request resumes the VM in place and waits for its health check: no restore, and no clock step (kvmclock reads the host clock again on the first instruction after the resume). |
| `idle` | The VM is snapshotted and stopped. A request restores the snapshot. |

A frozen app still sleeps at its original deadline (the snapshot is taken from the paused VM, which
is resumed for it), is never probed while frozen, and keeps its full admission budget under
ceiling admission; adaptive admission counts what it holds. With `reclaim = true`, memory pressure
freezes a running quiet app before it snapshots one. A document that makes an app run without
sleeping, a cron job, or an export resumes a frozen app first. Omit `freeze_after_ms` to freeze
nothing new; requests still resume those already frozen.

Freezing pauses the VMM alone: a paused guest runs nothing, so its tenant is not held, and no
lease can release it under a host that still holds it frozen. A frozen VM that will not resume is
not left paused for the next request to find the same way: the host stops it and boots the app
from cold, and the request waits for that boot. One whose deployment is being replaced is left to the
replacement instead, and the request waits for the new deployment to answer.

## Revision retention

An `on-request` instance can set an `expiry` policy with `idleMs` and an optional ISO 8601
`deadline`. The idle interval restarts with admitted traffic. The absolute deadline does not:
new requests are refused at that instant, including while an earlier request is still open.
The host lets admitted requests finish before stopping the instance and deleting its snapshot.
An indefinitely open stream can therefore delay deletion, but cannot admit more work.
Production should omit `expiry`; removing the policy makes a retained instance available again.
The control plane must remove an expired instance from desired state before its volume is deleted.
An expired revision answers `410 Gone`, is reported `expired` with `expiredAt`, and runs no more
cron jobs; a cron command still running when the revision goes idle holds it like an open request.

```json
"expiry": {
  "idleMs": 86400000,
  "deadline": "2026-11-01T00:00:00Z"
}
```

## First boot

`activation.firstBoot` says whether an `on-request` instance is booted once it is declared:

```json
{
  "desiredState": "on-request",
  "activation": {
    "sleepWhen": { "kind": "traffic-idle", "timeoutMs": 900000 },
    "firstBoot": "lazy"
  }
}
```

| `firstBoot` | On declaration |
| --- | --- |
| `eager` (default) | The host boots it, as it boots a `running` instance. |
| `lazy` | The host fetches its layers and routes its hostnames, but holds no memory for it and boots nothing. It reports `idle`, and its first request boots it as a wake with no snapshot does. |

A new `deploymentId` for a lazy instance that is not up replaces the declaration without booting
it. Its `expiry` runs from the declaration, booted or not.

<Callout title="Note">
  Only an `on-request` instance may set `firstBoot: lazy`: no request would ever boot anything
  else. A file that does this is rejected as a whole.
</Callout>

## What wakes it

Any inbound traffic: an HTTP request on one of its hostnames, or anything on a
[raw port](/docs/guides/raw-ports). The connection is accepted and held, then forwarded once the
app's [health check](/docs/guides/health-checks) passes. The client sees a slow first response,
not a refused connection.

## Snapshot lifetime

A snapshot holds the guest's whole memory on the host's disk. `activation.snapshotTtlMs` limits
how long it is kept without a wake. Past that it is deleted and the instance stays `idle`; the
next request boots it afresh from its layers and volume, as after a host reboot. Without
`snapshotTtlMs` a snapshot is kept until the next wake.

```json
"activation": {
  "sleepWhen": { "kind": "traffic-idle", "timeoutMs": 300000 },
  "snapshotTtlMs": 86400000
}
```

## Snapshot integrity

Before resuming a restored app, the host sets the guest's wall clock to the current host time and
releases its tenant. The app stays frozen until that succeeds. If the guest cannot synchronize its
clock, the host starts it from cold instead. (Firecracker's `clock_realtime` load option is not
used: it needs a host whose own clocksource let KVM save the real time, which a virtual machine's
`kvm-clock` does not, and Firecracker then refuses the load.)

A snapshot names the Firecracker that took it. After an upgrade of Firecracker, a sleeping app's
snapshot is refused by that name, and its next request boots it from cold, once, instead of
restoring; it is never an error.

Guests started before a host and guest-image upgrade keep running. If their init does not
support the freeze protocol, the host refuses sleep and retries after its normal backoff.
Redeploy the app to start it with the new guest image.

The host commits a snapshot only after its state, memory and integrity record have been synced
to disk: Firecracker syncs the state and memory files before it answers the snapshot request,
and the host syncs the integrity record and the directories that publish it. It verifies both files' sizes and SHA-256 hashes before restoring. A missing, damaged or
older snapshot without integrity records is discarded; the request starts the app from cold
instead. Files on its volume survive, but in-memory state does not.

A snapshot also records its Firecracker version, the host kernel and the CPU the guest was given.
It survives a host reboot onto the same kernel and CPU with the same Firecracker, and the next
request restores it; one the reboot changed any of the three for is removed when the daemon starts.

<Callout title="Snapshot cost">
  Hashing reads the state and memory once during sleep and once during wake. The guest stays
  paused until the snapshot is committed, so a failed commit can resume it without losing memory.
  This adds disk reads and latency proportional to the app's memory allocation.
</Callout>
